# Правила экономии токенов при работе с Claude API

Применимо к любому коду в этом репозитории, который вызывает Claude API
(`client.messages.create` / `client.beta.messages.create`). На момент
написания такого кода в репозитории ещё нет — `worker/src/telegram.js`
обслуживает только платёжный флоу без AI. Эти правила — база для того,
что появится позже (AI-ответы бота, обработка запросов и т.п.).

Принцип: сначала «бесплатные» оптимизации (не трогают качество ответа),
потом — оптимизации, которые торгуют качество на стоимость и требуют
измерения на реальных примерах, прежде чем включать их по умолчанию.

## Бесплатные оптимизации (не снижают качество)

### 1. Prompt caching для статичного контента
- Всё, что не меняется между запросами (системный промпт, статичные
  инструкции, описания инструментов), — в начало `system`, с
  `cache_control: { type: "ephemeral" }` на последнем таком блоке.
- Кэш — это префикс: любое изменение хотя бы одного байта до метки
  инвалидирует всё, что после неё. Не кладите в кэшируемую часть
  `new Date()`, случайные ID, несортированный JSON — это тихо ломает кэш.
- Порядок рендера запроса: `tools` → `system` → `messages`. Держите
  стабильные части раньше по этому порядку, изменчивые — позже.
- Проверяйте `response.usage.cache_read_input_tokens` в логах. Если он
  систематически 0 при повторных однотипных запросах — кэш не работает,
  ищите скрытый инвалидатор.

### 2. Гигиена истории и промпта
- Не отправлять всю историю чата — см. раздел «Управление историей» ниже.
- Не заставлять модель гадать формат ответа текстом — использовать
  `output_config.format` (structured outputs) там, где нужен
  машиночитаемый результат, вместо просьбы «ответь в формате JSON».
- Не дублировать в `messages` то, что уже есть в `system` (инструкции,
  контекст задачи) — платится дважды за одно и то же.

### 3. Гигиена выходных токенов
- `max_tokens` — не «про запас», а реалистичный потолок под конкретный
  тип ответа (см. таблицу ниже). Заниженный лимит обрывает ответ
  (`stop_reason: "max_tokens"`) и требует повторного запроса — это
  дороже, чем один раз подобрать разумное значение.
- Всегда проверять `stop_reason === "max_tokens"` в логах/мониторинге —
  это сигнал, что лимит занижен для этого сценария.
- Не просить модель повторять входные данные в ответе, если они не
  нужны пользователю буквально (эхо длинного контекста — чистый расход
  выходных токенов).

### 4. Пакетная обработка
- Для не-latency-critical задач (массовая разметка, генерация отчётов
  по расписанию и т.п.) — Batches API, минус 50% к стоимости.

## Оптимизации с компромиссом (нужно измерение перед включением)

### Управление историей чата
- Базовый вариант — окно последних N сообщений (для чат-бота обычно
  10–20 сообщений достаточно). Простое, предсказуемое, без доп. вызовов
  модели.
- Если продукт требует помнить длинный контекст (многодневные диалоги,
  факты о пользователе) — сжимать старую часть в summary отдельным
  дешёвым вызовом (Haiku), хранить `summary + последние N сообщений`.
  Не включать по умолчанию — усложняет отладку и добавляет доп. вызов;
  оправдано только если видно, что пользователи реально теряют важный
  контекст на окне из N сообщений.

### Выбор модели и effort
- Дефолт для диалоговых сценариев бота — Sonnet (текущее поколение).
  Haiku — для простых задач: классификация intent, сжатие истории,
  короткие детерминированные ответы. Opus — только когда это явно
  оправдано сложностью задачи (не для обычного чат-ответа).
- Двухуровневая схема экономии: дешёвая модель определяет
  тип/сложность запроса → простые запросы остаются на ней, сложные
  эскалируются на более сильную модель. Внедрять только после того,
  как есть данные, что доля простых запросов существенна.
- `effort` (`low`/`medium`/`high`/...) — рычаг того же типа, что и
  выбор модели: понижать для простых/массовых маршрутов, поднимать
  только там, где измерения показывают, что качество реально страдает
  на более низком уровне. Не задавать «на глаз» — сравнивать выход при
  разных уровнях на одном наборе примеров.

## Что нельзя делать ради экономии
- Не обрезать пользовательский ввод или файлы молча, чтобы уложиться в
  контекст — это баг, не оптимизация. Если контент не влезает —
  сообщать об этом явно и обсуждать чанкинг/суммаризацию.
- Не понижать модель/effort как реакцию на стоимость без проверки, что
  это не портит качество ответов пользователям — сначала измерить на
  выборке реальных запросов.
- Не убирать проверку `stop_reason` / `is_error` в `tool_result` ради
  упрощения кода — потерянная ошибка обходится дороже сэкономленных
  токенов на её обработку.

## Ориентиры по `max_tokens`

| Тип ответа | Значение |
|---|---|
| Короткий чат-ответ / подтверждение | 150–500 |
| Развёрнутое объяснение | 1000–2000 |
| Сжатие истории (summary) | 200–400 |
| Документ/отчёт | по факту задачи, обычно с `.stream()` при >4000 |

## Чек-лист перед деплоем AI-фичи
- [ ] Системный промпт помечен `cache_control`, повторные запросы дают
      `cache_read_input_tokens > 0`.
- [ ] История ограничена (окно или summary+хвост), а не отправляется
      целиком.
- [ ] `max_tokens` подобран под тип ответа, есть логирование
      `stop_reason`.
- [ ] Выбрана минимально достаточная модель/effort для сценария, а не
      «самая мощная на всякий случай».
